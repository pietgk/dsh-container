DSH CONTAINER ARCHITECTURE Phase 0 evidence, amended 2026-08-17
Architecture atlas

What are we actually building?

A trusted macOS CLI that builds a reproducible DSH image, boots it inside an Apple VM with a pinned Landlock kernel, mounts only four writable areas, and carries the Web UI over a Mac-loopback proxy without exposing DSH on the guest network.

The mental model

The image is the application filesystem. The custom kernel powers the VM security feature. The container combines that image with per-instance mounts. The CLI owns lifecycle. The proxy is the only inbound path. Gates decide when the next layer may be built.

Phase 1 is complete and all non-mutating checks pass. The architecture and dependency audit are accepted. Creating the first managed instance now requires live-egress and bind-workspace risk acknowledgement. Runtime gate

DRAWING 02

Image, kernel, VM, and container are different layers

This is the distinction that is easiest to lose when discussing one command called “container run.”

Image

What DSH runs

Exact source, built Web UI, runtime packages, Node, and static landlock-run. Shared when every build identity matches.

Kernel

What enforces Landlock

Apple's default kernel returns ENOSYS. The pinned kernel is mandatory for the filesystem sandbox to enforce a denial.

Container instance

What gains state

The disposable rootfs plus exact mounts, security controls, network, metadata, and proxy ownership. State survives container recreation.

DRAWING 05

The implementation sequence is a gated pipeline

We do not build a manager around assumptions that Phase 0 has already disproved.

Phase 1: manager foundation

CLI parsing, exact names, schema, partial-failure journal, audit records, kernel verification, Apple adapter, proxy ownership, and dry-run behavior.

Phase 2: vertical slice

init, start, status, logs, stop, delete, then lifecycle, security, transport-load, drift, and cleanup tests.

Phase 3: evaluation

Use DSH for representative app work, inspect its sessions and token data, and compare startup, memory, and interaction latency with a trusted host-native baseline.
